# 测试用例准则

开发方每个批次一份用例表，放在本目录，文件名和 `doc/开发记录/` 的同名批次对应（如 `B0 第一阶段.md`）。用例表回答三件事：这批**该测什么**（从策划案验收编号推出来）、**怎么测**（哪条自动测试或脚本）、**测过没有**（只按真实运行结果填）。

开发记录的"验收"一节只写结论和用例表链接，逐条结果以用例表为准。

试点批次：B0（2026-11-16）。做法取自外部 QA 流程（qa-sop / logic-test-sop）里能搬到小项目的部分，P4、Jenkins、飞书、AI 执行控制器等环境绑定的部分不用。

## 1. 用例表格式

```
| 用例 | 验收 | 测试点 | 前置 | 步骤 | 预期 | 方式 | 执行 | 结果 |
```

- **用例**：`<批次>-<两位序号>`，如 `B0-07`。一旦发布不改号；作废的写"作废"留着。
- **验收**：对应的策划案验收编号（`UI-03`、`SPACE-04`、`DEC-14`……）或策划案节号（`01 §2`）。一条用例可以对多个编号。
- **前置**：执行前必须成立的状态，要能造出来（清存档、`?dev=1` 开发入口、写坏的 localStorage 等）。造不出来的不准写"网页上无法构造"了事，要么补开发入口，要么把这条改成内核测试，要么标"本批不覆盖"并写原因。
- **预期**：看得见、判得了对错的句子，写具体值（"窗口左移 200 逻辑像素、宽高仍 480×270"），不写"正常""流畅"。
- **方式**：
  - `N` 内核 NUnit（`web/Moyu.Core.Tests/`），测试的 `Description` 以用例号开头；
  - `B` 浏览器验收脚本（`tools/verify/<批次>.mjs`），每个 `check` 的名字以用例号开头；
  - `M` 人工（目测画面、真桌面），执行时在"结果"写谁、在哪、看到了什么；
  - `S` 静态检查（grep 等），写出命令。
- **执行**：自动方式写测试方法名或脚本里的 check 名，便于对得上。
- **结果**：`通过` / `失败` / `未跑`，后面跟证据位置（构建号、结果 json、截图）。**只按真实运行结果填**，没跑的写"未跑"，不凭推断打勾。

表后附"本批不覆盖"清单：相关验收编号里这批不做的，逐条写原因（例：多人联机在 PC 端）。

## 2. 设计用例时逐条对照的覆盖标准

每个规则至少过一遍下面几类，写不出用例的那一类要能说清为什么不适用：

1. **正常路径**：验收句本身。
2. **分支**：规则里每个"如果……否则……"两边都有用例（放得下 / 放不下 / 不在区域）。
3. **边界值**：恰好在边上、差一点点（占地框正好贴住装饰、窗口正好贴到工作区右下）。
4. **反例**：不该发生的事确实没发生（拖动松开不选位、关菜单不切模式、按钮禁用时点了不改数据）。
5. **不变量**：操作前后不该变的量（拖窗时模式、地图、落点不变；收起恢复后位置不变）。
6. **状态组合**：同一操作在不同状态下（穿透开/关、收起/关闭、不同模式、不同地图）。
7. **持久化**：保存后刷新能恢复；存档坏了逐项回落。
8. **外部约束**：视口尺寸、缩放、焦点、别的窗口。

## 3. 失败了怎么办

跑出失败先归类，再动手：

| 类别 | 判据 | 处理 |
| --- | --- | --- |
| 实现错 | 用例符合策划案，代码不符合 | 修代码，重跑这条和同模块的用例 |
| 用例错 | 用例写错了预期或前置 | 改用例表，在开发记录里写一句为什么改 |
| 策划案缺口 | 策划案没说清，用例和实现都只能猜 | 停下，写进 `doc/策划案/00 总则/02 开发方待确认问题.md`，这条结果写"待确认 Qn" |

不允许为了变绿去放宽预期。

## 4. 执行时机

| 时机 | 跑什么 | 作用 |
| --- | --- | --- |
| 开发中 | `dotnet test web/Moyu.sln`；浏览器脚本可对开发服务器跑（`node tools/verify/<批次>.mjs http://localhost:5188/`） | 随改随查 |
| **推送前（主关卡）** | `node tools/verify/<批次>.mjs --release`：照 CI 的方式发布 Release 包、改写成线上子路径、挂在 `http://127.0.0.1:5199/zhuomianmoyu/` 上跑全套 | 功能验收；同时覆盖开发版测不到的 IL 裁剪、子路径、资源版本号、404 回落。全过才推，结果写回用例表 |
| **推送前，改到 `src/Core/` 时** | 变异测试，见 §5 | 检查内核测试是不是真的能抓到错。没有未处理的幸存变异才推 |
| 上线后（部署确认） | 对线上地址跑一次（不给网址就是线上） | 只确认部署：页面构建号等于这次提交、能加载、控制台无报错。全套顺手跑完，但功能结论以推送前那轮为准；这一轮失败而本地 Release 包通过时，先查部署和缓存 |
| 之后每批 | 上一批的脚本照样跑 | 回归 |

开发版（`dotnet run`）跑过不算推送前的验收：它不裁剪、不走子路径，和线上的包不是同一种东西。

## 5. 变异测试（内核）

测试全绿不等于测试有用：断言写得松、测试数据碰巧对称时，代码改错了测试照样绿。变异测试用 [Stryker.NET](https://stryker-mutator.io/docs/stryker-net/introduction/) 自动把内核代码改坏一处（`<` 改 `<=`、`&&` 改 `||`、删一行……），每改一处跑一遍测试；测试没变红的叫"幸存变异"，说明那段逻辑其实没被测住。

**什么时候跑**：只要这次改到了 `src/Core/`，推送前就跑。

```bash
dotnet tool restore
cd web/Moyu.Core.Tests
dotnet stryker --since:origin/main
```

- `--since` 只变异和 `origin/main` 相比改过的内核文件；这次也改了测试文件时会退回全量。全量一次约 1 分钟（B0 时 223 个变异）。每个里程碑全量跑一次（去掉 `--since`）。
- 报告在 `web/Moyu.Core.Tests/StrykerOutput/`（不进仓库），打开 `reports/mutation-report.html` 逐条看。
- 只变异 C# 内核；网页壳（Razor、`pet.js`）靠 §4 的浏览器脚本。
- 工具版本固定在仓库根 `.config/dotnet-tools.json`（4.14.2；更新版本的包本机 .NET 8 SDK 读不了）。

**幸存变异每条都要有结论，处理完才推送**：

| 类别 | 判据 | 处理 |
| --- | --- | --- |
| 真漏测 | 这处改坏了玩家或策划案能看出差别，只是没测到 | 补用例（进用例表、测试 `Description` 以用例号开头），补完重跑确认它被抓住 |
| 测试碰巧通过 | 测试数据太对称，改坏了也看不出（例：三张占位地图区域相同；用默认落点测"落点不动"） | 改测试数据或补一组不对称的数据，同上重跑 |
| 死代码 | 没人调用、或前面已经保证了永远走不到 | 删掉 |
| 等价变异 | 改了也不影响任何结果（例：循环上限本来就有余量） | 在那行代码上方写 `// Stryker disable once <变异类型> : <为什么等价>`，理由要让人一看就懂 |
| 策划案缺口 | 两种写法都说得通，策划案没定 | 写进 `02 开发方待确认问题.md` |

不定分数门槛，不为分数凑测试；结论记进本批用例表的运行记录（变异数、幸存数、各类各几条）。

**正控**：为一个缺陷或幸存变异补的测试，要确认它在修复前（或对着那个变异）是红的。变异测试重跑时幸存数下降就是正控；浏览器缺陷则对修复前的构建跑一次脚本。

## 6. 和试玩的关系

试玩不再负责"逐条验收"，只负责脚本测不了的：画面观感、手感、动画、真人连续玩。试玩发现的问题，修之前先补一条能复现它的用例。
