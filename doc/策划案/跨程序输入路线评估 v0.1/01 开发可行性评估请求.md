# 跨程序输入路线：开发可行性评估请求

资料编号：INPUT-EVAL-001；修订：0.1；日期：2026-11-17。
状态：用户已授权向开发询问实现难度并比较替代路线；这是评估请求，不是助手或桌面版已完成的声明，也不预先裁定新增输入范围。

## 1. 问题与用户最新指令

用户反馈：网页开着，切到其他程序进行键盘/鼠标操作，游戏不增加输入计数。已只读核对131cc2d：当前`web/Moyu.Web/wwwroot/js/play.js`仅注册document内真实输入；设置“后台输入”为演示开关，当前现象符合网页范围，但尚不能满足最终“在其他软件工作也推进钓鱼”的需求。

用户最初选择“保留网页游戏，另做需要安装运行的Windows输入助手，向网页发送动作计数”。总控补问首版是否只先计其他Windows程序、还是连浏览器其他标签页/地址栏也计时，用户最新答复为：“这个问题问开发，是否好做，不好做的话是否考虑直接做桌面版。”

因此：优先请开发比较可行性与成本；助手路线目前是优先评估候选，桌面试玩版是明确要求纳入比较的替代方案。不能把用户未选定的计数范围写成已定，也不能直接代其宣布转做桌面版。

## 2. 请比较的路线

| 路线 | 评估目标 | 必须说明 |
| --- | --- | --- |
| A：Windows助手＋现有网页 | Windows本地采集有效动作次数，经本机通道交给当前玩法页；网页继续负责动作、计数、节点和资产 | 实际HTTPS发布页如何连本机、目标浏览器/版本、权限/配对、后台冻结/断连、输入来源切换及游戏UI排除；是否需要额外扩展 |
| B：Windows桌面试玩版 | 让Windows程序承载游戏并接后台输入，先验证跨程序计数与现有玩法，Steam真实联机另计成本 | 哪些Core/Blazor页面/资源能复用，是否可先用薄壳承载现有界面；与既有Unity PC方向相比需要多少重做，不预锁引擎 |

不要求开发先给一套未经实测的完整实现。请分别给出“容易／中等／难”的判断、主要风险、能复用的部分、工作量范围与前提，并明确推荐哪条；若需要小验证，说明验证点和通过标准。工期估计由开发根据实际经验给出，不由策划编造。

## 3. 最需要开发回答的问题

1. **输入范围和排除成本**：首版仅覆盖Word/IDE等其他Windows程序，游戏浏览器在前台时仍由网页统计，是否明显更容易？若同时覆盖其他标签页/地址栏，可靠区分游戏管理操作、页面工作输入和系统输入需要什么额外适配？请给支持/不支持范围及原因。
2. **同一次操作只算一次**：助手和页面同时接触到按键/点击时如何避免双计？怎样排除游戏面板、选位、拖窗、收起头像、恢复、助手控制和配对操作？不能靠合成DOM事件绕过现有isTrusted检查，也不能为去重悄悄加50ms合并/输入限速。
3. **浏览器连接的实测**：现有GitHub Pages HTTPS地址能否在正常浏览器设置下连接本机服务？请测实际连接方式、混合内容/本地网络访问权限、来源校验和身份配对；不得要求玩家关闭浏览器安全功能。若必须额外扩展/证书/后台服务，请明确安装负担后再建议路线。
4. **工作中是否可靠**：切到外部程序、浏览器最小化/标签页隐藏时，输入是否能准确送达当前有写权的页面？页面被挂起、断连、关闭时怎样停采/停计，哪些已送达但未确认的数据可去重重试？不把不确定时段补造成输入，不向错误模式/地图投递旧计数。
5. **部署与维护成本**：两条路线各需装什么，是否能普通用户运行，杀毒/签名/升级/卸载等实际负担如何？哪些环境必须标不支持（如特定受保护界面），不能笼统承诺所有程序都可采集。
6. **给出推荐而非只留二选一**：说明A是否真的比B更省事；若助手连接、去重、后台恢复比做桌面壳更复杂，请直接推荐B并给出最小桌面试玩范围及可复用内容，供用户决定。

## 4. 两条路线都必须守住的已定合同

- 只统计动作资格/次数，不保存、发送键入文字、字符序列、剪贴板、应用标题或逐键时间线；必要的临时按下/释放状态只用于去repeat，不能变成长久键盘记录。
- 保持真实按下一次/点击一次的既有口径，repeat/松开/移动/滚轮/拖动不计，组合键各真实按下分别计数；管理输入不计。新增采集不能拦截正常办公输入或替用户输入。
- 页面与助手不得对同一操作分别发奖。一次接受的计数仍只归同一模式/地图，批量传输不得跳过节点或重试重抽。
- 现有500/1000路亚、每200至2000摸鱼、手竿30分钟、20条缸、售价/金币/抽取和房间模拟范围不因换输入路线改变。
- 网页关闭、主动关闭游戏小窗、停止助手/关闭实际后台采集后，不再新增跨程序计数；不把没有接收资格的离线时段补成奖励。后台输入与手竿计时不是同一通道。
- 任何本机桥接只向经过本次授权的玩法实例发送必要动作计数，不能变成其他网站可随意读取的键鼠服务；若本机服务方式成立，采用本机访问边界和有效配对，不向局域网开放控制。具体协议/端口/API由开发验证，不在本请求预选。
- 当前页面输入能力说明继续有效；在新路线真实接通前，不能把“后台输入”演示开关直接当作已实现。后续新增玩家可见状态/提示需在正式方案中列清逐字文案，不在评估阶段临时冒充已开放。

## 5. 技术核对线索（需按实际浏览器/Windows版本验证）

- Windows RAWINPUTDEVICE的RIDEV_INPUTSINK可使注册应用在不处于前台时接收输入，这是助手/原生宿主的候选基础；不代表网页本身获得系统输入能力，也不等于现成完成了过滤/去重。[微软文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputdevice)
- Chrome文档说明站点连接本地网络/本机软件可能涉及Local Network Access权限，且不同API和发布阶段的覆盖存在差异；不能只因某个localhost演示能通，就承诺生产HTTPS地址的所有浏览器都能通。[Chrome本地网络访问说明](https://developer.chrome.com/blog/local-network-access)
- 如考虑扩展的Native Messaging，它是扩展与本机程序之间的机制，需要注册本机宿主，不是普通网页直接调用；请将额外安装组件计入路线A成本，不默认用户已同意安装扩展。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

以上仅为官方核对线索，本次未开发/安装助手、未启用全局采集、未进行真实跨程序计数实验，不将文档支持写成项目实测通过。
